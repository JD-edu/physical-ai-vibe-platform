# PHYVIBE protocol v1

Protocol ID: `phyvibe-v1`. Bridge implementation release: 2.1.0. Studio 2.1.1 adds the servo profile; extension 0.1.2 includes executable servo blocks, received-angle reporters and guarded UART startup.

Studio and exported customer webapps share one independently started C++ bridge. Qwen generates a JSON skill plan; Studio validates it and supplies the command runtime. Qwen never invents transport frames or acknowledgements.

## First hardware test

1. Build the bridge: `npm run build:bridge`. Close the previous bridge instance, open `./physical/bridge-server/build/phyvibe-bridge`, then click **Start server**.
2. Update the MakeCode extension from `physical/microbit/main.ts`. Copy `physical/microbit/examples/protocol-v1-demo.ts` into a MakeCode project using this extension; set SSID, password and server PC LAN IP, compile and upload to micro:bit.
3. The ESP32 must run the TCP-command firmware in `physical/esp32/esp32_firmware/esp32_firmware.ino`. The whitespace-preservation change needs an ESP32 rebuild/upload when using payloads with leading/trailing spaces. The initial `a` demo does not rely on spaces.
4. Open the updated browser Studio or Electron 2.1.0. Select **Protocol v1 · micro:bit demo** above the prompt, connect to the bridge and choose Local Qwen.
5. Request: **Make a button that sends lowercase a and a temperature display.** Click the generated button. The monitor first shows TX waiting for ACK, then ACK after micro:bit finishes displaying `a`. Temperature arrives every two seconds.
6. Export a fresh `phyvibe-webapp.html`. It includes the same protocol client; older exported files do not update automatically.

The default **Legacy** profile sends raw commands to existing programs and reports execution as unconfirmed. Selecting v1 cannot upgrade the device program automatically. Bridge UI manual commands use legacy by default; check **Protocol v1: require micro:bit execution ACK** for a v1 device test.

## Skill catalog and device profiles

The executable catalog is `webapp/protocol-v1.js`, version 1. It supplies both Qwen's allowed skills and Studio's validation rules.

| Skill | Plan arguments | Payload / behavior |
|---|---|---|
| `display_sensor` | `key` | Bind a widget to incoming sensor data |
| `send_text` | `text` | Preserve the literal payload, including case and spaces |
| `set_servo` | `target`: servo/valve/mouth | `CMD:<target>:<angle>`, 0–180 |
| `set_motor` | none | `CMD:motor:<percent>`, 0–80 |

These describe Studio's templates. A device profile specifies what its installed MakeCode program actually supports:

| Profile | Supported operations | Execution confirmation |
|---|---|---|
| `legacy` | All existing skill templates; user supplies device handlers | Unconfirmed |
| `microbit-v1-servo` | `set_servo` target `servo`, integer angle 0–180; `a` display; `temperature` telemetry | Device ACK required |
| `microbit-v1-demo` | `send_text` with exactly `a`; `display_sensor` with `temperature` | Device ACK required |

For servo control, upload `microbit/examples/protocol-v1-servo.ts`, configure the actual signal pin, and select **Protocol v1 · micro:bit servo**. The payload `CMD:servo:134` becomes `V1:CMD:<id>:CMD:servo:134`; the extension applies PWM then sends OK. This ACK does not measure shaft position. Valve/mouth targets need their own pin configuration and device profile support.

The v1 demo deliberately rejects servo/motor skills, other text commands, and other sensor keys. Add a new device profile and matching MakeCode handlers together when extending the hardware. Protocol envelopes can carry other payloads; they do not themselves implement motors or servos. The demo generation provider is for legacy presets; use Local Qwen for v1.

Example plan:

```json
{"title":"Demo","widgets":[{"id":"send-a","type":"button","title":"Send a","actions":[{"skill":"send_text","text":"a"}]},{"id":"temperature","type":"metric","title":"Temperature","action":{"skill":"display_sensor","key":"temperature"},"unit":"°C"}]}
```

A button's actions execute sequentially. In v1, each action waits for a successful device ACK before starting the next. Failure, disconnect, or timeout stops the sequence.

## HTTP command interface

Browser → bridge:

```http
POST /api/command
Content-Type: application/json

{"protocol":"phyvibe-v1","command_id":"demo-001","command":"a"}
```

A newly accepted command returns **202 Accepted** with a record:

```json
{"protocol":"phyvibe-v1","command_id":"demo-001","command":"a","state":"sent","sent_count":1,"peer":"192.168.1.20","deadline_ms":1770000000000}
```

`sent` means queued to the ESP32 socket, not executed. Poll `GET /api/commands/demo-001` for the final state. Unknown IDs return 404. `/api/status` and `/api/health` also expose `protocol`, `ack_timeout_ms` and recent command records alongside existing telemetry fields.

| Validation | Result |
|---|---|
| ID: 1–32 ASCII letters, digits, `_` or `-` | Otherwise 400 |
| Payload: 1–64 printable ASCII characters, at least one nonspace; no CR/LF | Otherwise 400 |
| Same retained ID and identical payload | 200, return existing record; do not resend |
| Same retained ID and different payload | 409 `COMMAND_ID_CONFLICT` |
| No ESP32 command connection | 503 |
| More than one ESP32 command connection | 409; v1 requires exactly one device |
| 100 pending records with none available for eviction | 503 |

Legacy compatibility: POST `{"command":"a"}` without `protocol` broadcasts the raw line to connected ESP32 clients, returning 200 and `sent_count`. Legacy permits up to 256 Unicode characters; actual device buffers may impose smaller limits.

## Device wire format

Bridge → ESP32 over persistent TCP port 5001 → micro:bit UART:

```text
V1:CMD:demo-001:a\n
```

Split the header at the colon after the ID. Everything following it is the literal payload, so additional colons and spaces belong to the payload. Maximum command frame is 104 bytes before the framing newline, fitting the current 128-byte micro:bit receive buffer. LF terminates a frame; receivers may remove a trailing CR from CRLF but must not trim payload whitespace.

micro:bit → ESP32 UART → bridge HTTP `/receive` or `/exchange` (TCP receive also supported):

```text
V1:ACK:demo-001:OK
V1:ACK:demo-001:ERR:UNSUPPORTED_COMMAND
DATA:temperature:25
```

ACK ID rules match command IDs. ERR codes contain 1–48 uppercase ASCII letters, digits, or underscores. OK has no suffix. Send OK **after** the requested operation completes; receipt alone is insufficient. Unknown/late ACKs remain visible in RX history but do not change completed records. ACKs must arrive from the command device's IP address; this correlates messages and does not authenticate devices.

Numeric sensor telemetry remains `DATA:<key>:<value>`; sensor JSON `{"type":"sensor","k":"temperature","val":25}` remains supported by clients. Sensor data has no command ID or acknowledgement.

## Command lifecycle

```text
sent → acknowledged        device sends OK within deadline
sent → failed              device sends ERR within deadline
sent → timed_out           no matching ACK within 5000 ms
sent → connection_lost     device disconnects or bridge stops
```

All final states are immutable while retained. Timeout uses `ACK_TIMEOUT_EXECUTION_UNKNOWN`: the operation might have happened even if its ACK was lost. Disconnect or cancelled browser monitoring can also leave execution unknown. The client does not resend automatically. Any deliberate new execution must use a fresh ID.

The bridge retains up to 100 records in RAM and evicts the oldest finished record as needed. Restarting the process loses records. MakeCode caches the last eight completed ACKs and replies to a duplicate ID without rerunning its handler. These bounded caches do not guarantee exactly-once execution after eviction, restart or simultaneous duplicate delivery; clients must generate unique IDs and avoid automatic execution retries.

The current API has no authentication and is intended for a trusted local network. Multi-device addressing, persistent history, command cancellation, capability discovery, actuator drivers and authentication are future extensions, not v1 features.

## Source map and validation

- `webapp/protocol-v1.js`: versioned skills/profiles and reusable ACK-waiting client.
- `webapp/app.js`: Qwen prompt, validation, Studio actions and standalone export integration.
- `physical/bridge-server/src/bridge_server.cpp`: v1 HTTP routes, framing, command states and ACK tracking.
- `physical/bridge-server/src/bridge_window.cpp`: manual v1 test option and bidirectional monitor.
- `physical/microbit/main.ts`: command parsing, success/error ACK blocks, duplicate-result cache and sensor helper.
- `physical/microbit/examples/protocol-v1-demo.ts`: initial supported device behavior.
- `physical/esp32/esp32_firmware/esp32_firmware.ino`: transparent command forwarding without trimming payloads.

```bash
npm test
npm run test:bridge
```

The bridge tests exercise real local HTTP/TCP sockets with a simulated ESP32. MakeCode tests type-check/transpile against host stubs and test the parser/ACK logic; they are not a MakeCode target build or a flashed-board test. Compile/upload the example in MakeCode and complete the hardware test above before relying on real-device execution confirmation.
